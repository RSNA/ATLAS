ATLAS Crosswalk: CHAI, Hugging Face, and ACR AI Documentation Standards

This document maps the ATLAS 2026-12 schemas (model.json, dataset.json) against four other AI model/dataset documentation efforts: the Coalition for Health AI (CHAI)'s Applied Model Card, Hugging Face's Model Card and Dataset Card metadata, the American College of Radiology (ACR)'s Assess-AI registry and AI Central directory, and the foundational Google Model Cards framework (Mitchell et al., 2019) that both ATLAS's and CHAI's field vocabularies descend from.

Methodology and source confidence

Findings below come from three dedicated research passes (one per standard) plus the author's own work on ATLAS. Network access in this environment blocked several primary domains (arxiv.org, research.google, chai.org/mc.chai.org/registry.chai.org, acr.org and its subdomains), so confidence varies by standard — stated explicitly so this document doesn't imply more certainty than the sources support:

What each standard actually is

These four are not all the same kind of artifact, which matters for reading the tables below:

  • ATLAS (model.json/dataset.json) — a formal JSON Schema, authored per model/dataset, with three conformance profiles (minimal, procurement-ready, regulatory-ready).
  • CHAI Applied Model Card — a formal XML Schema, authored per deployed health-AI application (explicitly scoped to "the application in a health use case," not a bare model; CHAI recommends a revised card when the underlying system changes, e.g. swapping foundation models). Still self-labeled "draft" as of the version read. Source: coalition-for-health-ai/mc-schema.
  • Hugging Face Model/Dataset Cards — YAML frontmatter in a repo's README.md, validated server-side at push time against a documented (but not formally schema'd) contract, plus a Mitchell-et-al.-based prose template for everything the YAML doesn't cover. Source: huggingface/hub-docs.
  • ACR Assess-AI — a live, post-deployment performance-monitoring registry (part of ACR's National Radiology Data Registry), not a pre-deployment authoring format. It ingests case-level data via HL7v2/FHIR/DICOM/DICOMweb/CSV and reports aggregated performance back to sites. ACR AI Central — a curated directory of FDA-cleared imaging AI products (read-only; ACR populates it from FDA filings plus voluntary vendor disclosure), not an authoring schema either. Neither publishes a public machine-readable schema.
  • Google Model Cards — the original prose template (2019) that the "Model Details / Intended Use / Factors / Metrics / Evaluation Data / Training Data / Quantitative Analyses / Ethical Considerations / Caveats and Recommendations" section structure traces back to. No machine-readable schema at all — it predates that concern.

Where Hugging Face is more structured than ATLAS is the shape of the data (dataset_info's features/splits/byte counts, which ATLAS has no equivalent for); where ATLAS is far more structured is the clinical characterization (demographics, age range, site count, confidentiality/re-identification risk), which Hugging Face's schema doesn't address at all.

Two concrete, specific comparison points worth flagging:

  • CHAI's three-pillar structure has no ATLAS analog. ATLAS's Factors/Subgroup mechanism covers fairness disaggregation for any individual result, but nothing in ATLAS declares "this metric is a safety/reliability metric" vs. "this metric is a usefulness/efficacy metric" the way CHAI's schema does by construction (three separate blocks).
  • Hugging Face's verifyToken is a sharper provenance mechanism than ATLAS's Provenance enum. ATLAS currently only records a self-declared Claimed/Observed distinction; Hugging Face's token is cryptographic proof tied to its own evaluation infrastructure.

ATLAS's design — any individual Results[] entry can carry a Subgroup, regardless of which metric it is — is more flexible than CHAI's approach of segregating fairness metrics into their own block, since it lets the same metric be reported both overall and per-subgroup within one Model performance entry.

Where ATLAS already leads

  • Regulatory authorization structure — a repeatable, per-jurisdiction Authorizations[] array with pathway-specific identifier validation, versus CHAI's single free-text field or ACR's read-only directory entries.
  • Integration / interoperability detail — DICOM/DICOMweb/HL7v2/FHIR/IHE coverage with no analog of comparable depth in any standard reviewed.
  • Dataset-role vocabulary — a 13-value, ROADMAP-backed enum shared identically across Model.Datasets[].Role, Dataset.Models[].Role, and Dataset.Partitions[].Partition; none of the other standards have a comparably granular, controlled vocabulary for this.
  • Reciprocal model↔dataset linkage — both Role-tagged. CHAI has no separate dataset document to link to at all; Hugging Face's datasets: field is an untyped flat list of repo IDs with no role tagging.
  • Conformance tiers — the only standard here with formal, machine-checkable tiers (minimal / procurement-ready / regulatory-ready).
  • Clinical dataset characterization — Subset's demographic/ age-range/site-count breakdown has no analog in Hugging Face's dataset_info or in CHAI (a single free-text characterization field).

Candidate improvements (for consideration, not applied here)

These are observations from the crosswalk, not changes made to the schema — several overlap with gaps this project's own conformance-profile work had already flagged independently.

  1. Targeted patient population. Already tracked as DEFERRED in procurement-ready.json. Now confirmed against two independent external precedents (CHAI's dedicated field, ACR AI Central's listing category).
  2. Stakeholders consulted. CHAI has a dedicated field for who was consulted during development; ATLAS has no analog.
  3. Metric "pillar" tagging. CHAI requires every metric to live under Usefulness/Fairness/Safety. ATLAS could add an optional enum to Model-performance-results if that framing would be useful — a judgment call, since ATLAS's current design is more flexible in a different way.
  4. Independent-verification provenance. Hugging Face's verifyToken cryptographically proves an evaluation ran on independent infrastructure. ATLAS's Provenance enum is self-declared only.
  5. License as controlled vocabulary. Hugging Face validates license against a known identifier list with an other escape hatch; ATLAS's License.Text is free text.
  6. Human-oversight measures — already tracked as DEFERRED in regulatory-ready.json. This crosswalk found no external precedent for a dedicated structured field in CHAI, Hugging Face, or ACR either — none of the four standards reviewed has operationalized this HTI-1/EU AI Act Annex IV requirement as a discrete field yet.
  7. Base-model relation granularity. Hugging Face's base_model_relation enum (adapter/merge/quantized/finetune) is more specific than ATLAS's free-text Foundation model field.
